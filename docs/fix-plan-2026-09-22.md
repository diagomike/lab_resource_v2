## Workstreams, in build order

The order puts small, independent fixes first, then shared building blocks, then the draft-state work that depends on them. Each workstream ends with `tsc`, `npm test` and `npm run build`, plus a check in the in-app browser against `lrms_v2_e2e`, and one commit.

### WS-1 · Password reset and one-time sign-in links
1. **Reproduce first.** Request a reset for an ACTIVE CSE account on :3100 with the mail sink running, then look for a `PasswordReset` row and a line in `index.jsonl`. If it works, the earlier failure was the invited-account case: fix that path (step 2) and note it. If it doesn't, debug the route (`app/api/auth/forgot-password`) → `forgotPassword` → `mail.send`.
2. **Invited accounts:** if `forgot-password` gets an INVITED email, reissue the invitation (same throttle) instead of doing nothing silently. The account-enumeration posture is unchanged, because the response is identical either way.
3. **One-time sign-in link:** add "Email me a sign-in link" on the login page.
   - A new `LoginLink` table (hashed token, 15-minute TTL, single use, same 3-per-hour throttle as resets).
   - `POST /auth/login-link` and a page at `/login/link?token=…` that consumes the token and creates a normal session.
   - Only for ACTIVE accounts with a password. Invited accounts get the invite instead.
4. Tests: token single use, expiry, throttle, an INVITED account getting the invitation, and a DISABLED account getting nothing.

### WS-2 · Links in People & roles → Manage
In `PersonManageModal`:
- **INVITED:** a "Copy invite link" button. It calls the existing `resend-invite` (which issues a fresh token and invalidates the old one) and shows the URL inline with Copy, next to a "sent by email too" note.
- **ACTIVE:** a "Create password-reset link" button. A new admin endpoint issues a `PasswordReset` and returns the URL for the admin to hand over directly. It emails the person too, so it can't happen silently. It's logged, and allowed only for SYS_ADMIN, or a MANAGER for people in their own subtree (the same reach as `resendInvite`).

### WS-3 · Hierarchical tree picker (shared component)
- A new `components/TreePicker.tsx`, built on the `CategoryCombobox` pattern from `AddModal` (portalled, keyboard-navigable, type-to-filter):
  - options render as an **indented tree** with a category icon and expand/collapse;
  - while filtering, a match shows with its ancestors, greyed, for context;
  - the selected value shows as its name, with its path as a subtle second line.
- Server-side, `ContainerOptionDto` already carries `path`. It needs `parentId` (or ids along the path) so the client can nest reliably when two containers share a name.
- Replace all six `" / "` selects with it. Also use it for the **owning / current unit** pickers, fed from the org hierarchy (College → Department → Office), so units nest too.

### WS-4 · No-flicker saves in the register
- `useRegisterState`: `setRows(null)` only when mode, filters, scope, view or page change. A `refetch()` after a write keeps the current rows on screen and swaps them in when the response arrives. Add a small "Saving…/Updated" indicator in the header instead of the skeleton.
- Keep `expanded`, the selection, the scroll position and the open inspector across a refetch.
- The inspector patches its own item from the write result (or does a single-item fetch) instead of remounting.
- Check it by timing a status edit: no skeleton frame, and expanded rows stay expanded.

### WS-5 · Bulk create: unique names, systematic numbering, preview
Numbering scheme (lives in `lib/domain/instantiate.ts`, so it can be tested as a pure function):
- **Sibling scope:** items with the same `parentId` that aren't deleted. For top-level items, it's other top-level items with the same owning unit.
- **Base name** = the Name field, which now defaults to the category name (comment 6).
- **Existing numbers:** siblings whose name matches `^<base> (\d+)$`, case-insensitive. A plain `<base>` with no number counts as taking slot 1.
- **Allocation:** hand out the **lowest free numbers first**, filling gaps, then continue past the maximum. Example: 01–20 with 12 deleted, add 5 → 12, 21, 22, 23, 24.
- **Padding** = `max(2, digits of the largest number in the final set)`, so 99 → 100 moves the width to 3 for the new items only. Existing names are never renamed.
- **A single item** (count 1) gets a plain `<base>` only when no sibling uses that base. Otherwise it's numbered by the same rule.
- **Template parts** ("Monitor 1", …) are numbered inside their own new subtree only, as today.

Uniqueness rule, enforced by the server on `createItem`, rename (`setName`) and `moveInTree`:
- **No two live siblings may share a name**, compared case- and whitespace-insensitively. The server checks this inside the write transaction under a per-parent advisory lock, so two concurrent bulk adds can't both take 21.
- Existing duplicates in the DB aren't migrated. They only block a *new* collision. A one-off report script lists them.

Preview before applying:
- The dry run (`POST /resources/items/changes/preview`) returns the **planned names** and the resulting subtree size for `createItem`.
- AddModal's **Confirm & create** becomes **Preview…**. It opens a preview modal that shows the destination's existing children with the new rows highlighted in place, in sorted order, then **Apply** or **Back**.

### WS-6 · Category icons: the full set, searchable
- Swap the curated registry for **all lucide icons**, about 1,600: lucide-react 1.34's `icons` map, or `DynamicIcon`, loaded lazily so the register bundle doesn't grow. Existing keys are already lucide PascalCase names, so no data migration is needed.
- The server's `iconKey` check validates against the full lucide name list (a generated static JSON of names, kept server-side).
- `IconPicker` becomes a searchable combobox with an icon grid or list. Each option shows the icon and its name, and matches lucide's own tags (search "curtain" → `Blinds`, "water" → `Waves`), like the Add-resources category picker.

### WS-7 · Group-by view in the register
- A new register mode, **Grouped**, with a stackable **Group by** chooser, persisted in the URL: owning unit, current unit, department, custodian, category, category group, status.
  - **Unit** keys nest along the org hierarchy (College → Department → Office), not as flat buckets.
  - **Department** means the Department-kind ancestor of the owning unit.
- Grouping applies to **top-level resources**. Each lab keeps its own nested contents under its group, so the hierarchy is never flattened. Group headers show counts and a status summary (reusing rollup's aggregation).
- **University resources defaults to Grouped by Owning unit.** `/register` keeps Tree as its default. Both remember the last choice per page.
- Group headers are collapsible, and "expand to level N" works.

### WS-8 · Draft mode stages edits automatically
When the owning department has drafts ON, an edit made anywhere in the register (the inspector, bulk edit, AddModal inside a lab) by someone who may stage it is **staged instead of refused**:
- The write door (`mutate.ts`) gains a `stage-if-draft` path. Stageable kinds go to `stageDraftChange` against the item's **lab**, meaning its top-level ancestor (the same subtree rule `assertStageable` uses). It returns `{ staged: true, draftChangeId }` instead of a 403.
- Non-stageable kinds (custody, ownership, cross-lab moves) are still refused with the transfer pointer.
- UI: the inspector shows the field with a "Staged, pending approval" marker and the draft value. The register row gets a draft badge, and a toast offers "Review & submit" (→ WS-9).
- Who stages is set by Decision D6 below.

### WS-9 · Lab states page: Current · Draft · Ideal
A new sidebar item **Lab states** (next to Approvals). It's one page with **horizontal tabs**. Each tab is a full register-shaped view, reusing `ResourceTable`, the grouping from WS-7 and the scope/filters:

| Tab | Shows | Actions |
|---|---|---|
| **Current** | The live register, the same as `/register` | — |
| **Draft** | The live register **with every open and submitted staged change applied as an overlay**: changed fields show old → new, added rows are green, deleted rows are struck through, and each lab shows its commit state (open, submitted, rejected with the reason, stale) | Custodian: edit, withdraw, submit. Head: approve or reject the lab's batch right here |
| **Ideal** | Per lab, per category: **Ideal · Current · Draft · Gap**, grouped the same way. It's the target purchasing calculates against, with a pending-ideal proposal shown next to the approved one | Custodian: edit targets inline, submit. Head: approve or reject |
| **Approvals** | The lab-commit inbox (moved here from the Approvals page, which then links to it) | Decide |

- The diff lines use the existing `describeChange` wording, so nothing reads as an opaque card.
- A new read endpoint returns one lab's (or the scope's) staged overlay, so the client doesn't recompute it.
- `LabDraftPanel`'s "Manage draft…" opens this page on the Draft tab, filtered to that lab. That removes one of the two duplicate editors.

## Decisions for the user (needed before the named workstream starts)

- **D1 (WS-9): how detailed is "Ideal"?** Today the ideal is a count per category per lab (Computer 6, Chair 30), and purchasing already works from that. The recommendation is to keep that model and present it register-shaped (above). The alternative is a full named item tree for the ideal state ("Workstation 01–30, each with a monitor…"). That's a much larger data-model change, and purchasing only needs counts.
- **D2 (WS-5): name-uniqueness scope for top-level items.** The recommendation is per owning unit, so CSE and SE could each have a "Lab 01". The alternative is university-wide.
- **D3 (WS-1): sign-in links for every account**, or only users who opt in? The recommendation is everyone, 15-minute TTL, single use.
- **D4 (WS-2): who may create a reset link for someone else?** The recommendation is SYS_ADMIN, plus a MANAGER for their own subtree. The person is always emailed too.
- **D5 (WS-6): ship every lucide icon?** The recommendation is yes, lazily loaded only in the category editor and picker, with the rest of the app keeping one icon per category.
- **D6 (WS-8): with drafts on, are the head's and the admin's own edits staged too?** The recommendation is that the custodian's and the head's edits are staged, and the head can approve their own batch only if they aren't the author (someone else has to decide). SYS_ADMIN keeps direct edit as the break-glass path, and the change log records it.
